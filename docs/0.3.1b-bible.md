# 0.3.1b bible

`0.3.1b` is the clean reconstruction of the useful work attempted on
`0.3.1a`. It starts from `main`; `0.3.1a` remains an archive, test case,
and source of ideas. It is not a branch to merge wholesale or a bug-fix chain
to continue extending.

The order of work is intentional:

1. logging;
2. cosmetics and general decomposition;
3. multiplayer structure;
4. Freeplay behavior;
5. streamed/transferred audio transitions;
6. real-network hardening.

This gets broadly useful, lower-risk work settled before returning to the
Freeplay trenches. It also ensures the next multiplayer implementation has
useful diagnostics before it needs them.

## Branch policy

- Fork `0.3.1b` from current `main`, not from `0.3.1a`.
- Keep `0.3.1a` intact. Do not rebase, squash, or delete it while reconstruction
  is in progress.
- Prefer small cherry-picks for isolated changes. Reimplement intertwined
  changes manually after comparing the final `0.3.1a` code and its history.
- A cherry-picked commit is not accepted merely because it applies cleanly.
  Review its complete diff against `main`, run focused tests, and run the
  required build.
- Do not carry temporary protocol adapters or state migrations. Multiplayer is
  experimental and compatibility is deliberately scorched-earth.
- Bump the multiplayer protocol and Firebase rules once, when the reconstructed
  wire contract is coherent. Do not reproduce the protocol 13 through 16 march.
- Keep the version in a valid form for the existing toolchain; the branch name
  and product label may be `0.3.1b` independently of the exact package-version
  spelling.

## What the 0.3.1a review established

The branch was not a total loss:

- `npm run check` completed with zero errors and zero warnings.
- 114 focused multiplayer/store tests passed and 7 were skipped.
- The production PWA build completed successfully.
- The session split, per-peer Freeplay renderer, client-owned transferred-file
  timeline, Freeplay queue, shuffle history, and per-pair persistence are useful
  designs.

It is nevertheless not a merge candidate:

- 27 commits changed 143 files with approximately 12,700 insertions and 4,800
  deletions.
- The streamed-audio path accumulated timers, cushion estimators, fixed margins,
  a global readiness boolean, a drain timestamp, persistent silence, and several
  overlapping asynchronous attach paths.
- The investigation document repeatedly revised earlier `DONE` conclusions
  after live-network testing.
- Tests cover protocol validation, pure helpers, receiver estimation, and audio
  primitives, but not the complete client transition choreography where the
  reported races occurred.
- The host/client split improved navigation, but the resulting host and client
  modules remained large closure-based controllers with substantial shared
  mutable state.

The final assessment was: workable product model, salvageable decomposition,
audio implementation needing substantial replacement.

## Phase 1: logging first

The three `0.3.1a` logging commits (`22e0473`, `7ed99db`, `7953c20`) are a
prototype and visual reference. Do not cherry-pick the series wholesale.

### Keep

- A transient in-memory ring buffer. Logs are presentation/diagnostic state and
  must never be persisted.
- Typed levels and sources.
- Global `error` and `unhandledrejection` capture, with the benign
  ResizeObserver errors filtered.
- A desktop-style Logs tool window with filtering, copy/export, clearing, and
  useful columns.
- Cross-window collection through `BroadcastChannel` where available.
- Explicit structured logging at playback, decode, file, library, tools,
  multiplayer, and Freeplay ownership boundaries.

### Replace

- Do not make every window rebroadcast its complete aggregate buffer one entry
  at a time. Each context owns only the entries it originated.
- A history request carries a request ID. Each live context answers once with a
  bounded batch of its own entries. The requester merges and deduplicates the
  batches.
- Broadcast new entries incrementally. Batch notification/render work when a
  history response contains many entries.
- Do not clone the full 3,000-entry list for every arriving entry. The store may
  publish snapshots at a controlled cadence while the Logs UI is subscribed.
- Give debug capture and/or debug console mirroring an explicit control. Normal
  playback progress must not become permanent four-times-per-second log traffic.
- Initialize logging consistently in every page entrypoint, including Editor.
- Close listeners/channels when a context is actually destroyed in tests or
  reusable tool shells.

### Logging acceptance

- Opening Logs after several windows have accumulated the maximum history does
  bounded batch work rather than an entry-by-entry replay storm.
- Duplicate history responses never create duplicate rows.
- A malformed or non-cloneable detail object cannot break logging.
- Logs remain usable when `BroadcastChannel` is absent.
- Exported diagnostics contain app version, window/context, timestamp, level,
  source, message, and normalized details.
- There is a focused test for multi-window history exchange at the retention
  limit, not only one- and two-entry examples.
- All application and tool entrypoints either initialize logging or explicitly
  document why they do not.

## Phase 3: multiplayer decomposition

Use `6d1ff83` as the primary reference for splitting `multiplayer-session.ts`.
It may be cherry-picked early in this phase if its diff remains behavior-neutral
after the preceding work; otherwise reproduce the split manually.

Target ownership:

- `multiplayer-session.ts`: public controller, shared store, lifecycle wiring,
  and reset/destroy coordination only;
- `multiplayer-host.ts`: host session and host command behavior;
- `multiplayer-client.ts`: client session and client command behavior;
- `multiplayer-signaling.ts`: Firebase initialization, rooms, directory, and
  signaling lifecycle;
- `multiplayer-peer.ts`: peer connection, channels, send buffering, ICE state,
  and bitrate application;
- `multiplayer-source-transfer.ts`: chunked source-file transfer;
- `multiplayer-protocol.ts`: versioned wire types, bounds, and validation;
- `multiplayer-types.ts`: shared internal session/peer types;
- `multiplayer-utils.ts`: pure helpers only.

Do not treat moving a 3,000-line closure into two 1,400-line closures as the end
state. Extract stateful transition owners when their invariants can be named and
tested. In particular, audio delivery and playback preparation must not remain
incidental booleans scattered through the client controller.

### Lifecycle invariants

- Exactly one active role: idle, hosting, or client.
- Reset is idempotent and invalidates every pending asynchronous continuation.
- Reconnect work belongs to one owner and cannot survive an explicit leave.
- Peer removal destroys its Freeplay renderer, transfer queues, timers,
  navigation state, and preparation state.
- Firebase cleanup remains best-effort with registered disconnect cleanup as the
  fallback.
- Protocol validation occurs before messages reach behavioral owners.

## Phase 4: reconstruct Freeplay semantics

Port concepts from these commits and the final branch rather than replaying the
entire fix chain:

- `a142d51` — timeline-passive transferred-file Freeplay;
- `362463c` — client-owned Freeplay queue;
- `6e173d3` — local-style shuffle/repeat navigation;
- `92c8de2` — reconnect/restore and persisted last-session behavior;
- `81c9bd1` — explicit Freeplay delivery preference and host-authoritative
  buffer setting.

### Required model

- Freeplay is opt-in per paired host/client relationship.
- The host remains authoritative for its catalog and file materialization.
- Each active Freeplay peer has an independent host-side selection and renderer.
- Freeplay never mutates or routes through the host's shared playlist or player
  controller.
- The client owns its Freeplay queue as an ordered list of host-catalog IDs.
- Queue updates are bounded, deduplicated, and validated at the protocol edge.
- The host owns navigation execution using local-equivalent linear,
  shuffle-history, and repeat semantics.
- Leaving Freeplay clears ephemeral host peer state. Persist only the intentional
  per-pair client resume state.

### Delivery modes

Treat delivery as an explicit discriminated mode, not the interaction of two
booleans:

- `none`: host audio disabled or unavailable;
- `stream`: host renderer owns playback and sends audio over WebRTC;
- `source-file`: host serves the materialized file and the client owns playback
  time locally.

For `source-file`, the host is timeline-passive. It publishes the selected track
and serves/re-serves the file, but it does not synthesize progress, auto-advance
from a wall clock, or mirror play/pause/seek. The client's local ended event is
the sole automatic-advance trigger. Repeat-one is local replay.

For `stream`, the host-side per-peer renderer owns the timeline and ended event.
The client is a sink and sends transport commands to the host.

Switching delivery mode is a state transition with a new generation ID. It is
not inferred later from whichever `audio` and `playback` messages arrived most
recently.

## Phase 5: replace the audio transition stack

Do not port the final `0.3.1a` preroll/drain implementation verbatim. Preserve
its measurements and failure reports as test cases.

### Stable pipeline design

For each Freeplay peer, create one stable host-side
`MediaStreamAudioDestinationNode` and attach its track to the WebRTC sender once.
A silence anchor keeps the wire alive when no renderer is connected. Streamed
renderers connect behind that destination; changing tracks changes the input to
the stable destination, not the sender track.

On the client, create one audio element and one Web Audio route for the receiver
track per session. Keep the pipeline alive across streamed track changes. Use a
gain stage to keep preparation/idle audio silent and to ramp audible playback.
Do not clear and recreate the element/source node merely because a different
track is selected behind the same receiver track.

The stable pipeline is intended to remove the conditions that produced retained
tail replay, cold source-node startup, and overlapping attach continuations. If
Chromium behavior disproves that assumption, record the minimal reproduction
before adding another timing workaround.

### Generation-keyed preparation

Every selection/delivery transition receives an opaque preparation ID. The
protocol should express the relationship directly, for example:

```text
host:   prepare { id, trackId, delivery }
client: ready   { id }
host:   playback starts only if id is still current
host:   state   { id, trackId, playback }
```

- Readiness is never a session-wide boolean.
- Stale `ready`, file chunks, statistics polls, timers, and renderer completions
  are ignored because their ID no longer matches.
- A single generation/abort owner cancels all asynchronous work for the previous
  transition.
- The host cannot start a streamed renderer until the matching client pipeline
  is ready when readiness gating is required.
- Clients that refuse audio and `none` delivery acknowledge immediately without
  blocking the host.
- Source-file readiness means the matching file is completely received and
  locally loadable, not merely that transfer began.

### Buffering controls

- Retain the listener-buffer setting as a Goldilocks control if measurements
  show that Chromium's `jitterBufferTarget` materially helps.
- The host may remain authoritative for the intended session buffer, but the
  effective value and browser support must be observable in diagnostics.
- Fixed margins and polling budgets require named evidence and bounds. They must
  not become correctness mechanisms when a state/generation invariant can solve
  the same problem.
- Diagnostic sampling must not delay the audible critical path.

### Audio acceptance matrix

Automated tests with fake timers and fake audio/RTC adapters must cover:

- idle to first stream;
- stream A to stream B;
- stream to source-file to stream;
- source-file A to source-file B;
- rapid A to B to C before B becomes ready;
- pause, stop, seek, next, previous, shuffle, and every repeat mode;
- client audio refusal and later enablement;
- host audio disable/enable and delivery-mode changes;
- autoplay-suspended AudioContext;
- failed renderer construction;
- failed sender replacement or channel send;
- failed/interrupted source transfer and retry;
- reconnect during prepare, transfer, playing, and paused states;
- host restart with persisted queue/current-track restoration;
- stale readiness, stale playback, stale file chunks, and stale ended events.

Tests must exercise the orchestrator, not only pure helpers and the audio service
in isolation. There should be assertions that obsolete generations produce no
state changes after cancellation.

### Phase 5 implementation status (2026-08-09)

The deterministic reconstruction is implemented on `0.3.1b`; live-network
verification remains Phase 6 work.

- Protocol 14 uses one immutable generation ID for delivery, playback,
  preparation/readiness, source transfer/retry, and ended events.
- Each Freeplay peer owns one silent, stable host sender track. Renderer changes
  reconnect inputs behind that track and never replace it between selections.
- The client owns one stable receiver element and Web Audio route per session.
  Delivery changes mute/ramp its gain without rebuilding the route.
- `multiplayer-client-transition.ts` owns generation readiness and rejects stale
  playback, preparation, source completion, and ended work.
- Source reads and data-channel sends fail into bounded retry/reconnect behavior;
  reconnect replacement destroys the previous peer renderer first.
- No preroll estimator, retained-tail timer, drain margin, or session-wide
  readiness boolean was carried over from `0.3.1a`.

Focused transition tests cover first stream, repeated streamed generations,
stream/source-file/stream, rapid supersession, audio refusal and re-enablement,
suspended audio, source-read failure, and control/media channel send failure.
The complete repository test, check, and build results should be recorded at
handoff; browser and real-network observations must not be inferred from them.

## Phase 6: real-network verification

Only begin timing adjustments after deterministic orchestration tests pass.

Use at least:

- two same-machine windows for fast iteration;
- two devices on normal Wi-Fi;
- a mobile client over a materially different network path;
- a relayed/TURN path where practical;
- background/foreground and device-lock transitions on mobile.

Before trusting a development run, confirm that a stale production service
worker is not serving an old hashed bundle. Development resources should be
coming from source modules rather than an old Workbox precache.

For each delivery transition, capture:

- preparation ID and delivery mode;
- sender/receiver track identity and lifecycle;
- AudioContext state;
- readiness send/receive times;
- effective jitter-buffer target and sampled level where supported;
- renderer start and route gain transition;
- first audible sample latency;
- cancellation/supersession events.

A real-network observation may justify a browser-specific workaround, but every
workaround needs a bounded fallback, an observable log, and a regression test
for its control flow.

## Commit discipline for the reconstruction

Prefer commits that each answer one question:

1. Can logging collect and export bounded cross-window diagnostics?
2. Can the cosmetic work land without multiplayer behavior changes?
3. Can multiplayer be split without behavior changes?
4. Can Freeplay queue/navigation work without audio?
5. Can source-file Freeplay work with a client-owned timeline?
6. Can a stable streamed pipeline play one track?
7. Can generation-keyed preparation switch tracks and delivery modes?
8. Can reconnect restore the intended state?
9. Do real networks require additional bounded buffering behavior?

Avoid commits titled `attempt`, `further fixes`, `remaining points`, or numbered
passes without a stated invariant. If a change cannot explain the invariant it
establishes, it is probably another layer on the quagmire.

## Definition of done

`0.3.1b` is ready to replace the experiment branch when:

- logging is bounded, cross-window, exportable, and initialized consistently;
- selected cosmetics have landed without dragging in unrelated branch state;
- the main composition root is lean and multiplayer ownership is explicit;
- standard shared multiplayer still works;
- Freeplay queue, navigation, persistence, and both delivery modes work;
- the audio client uses a stable pipeline or has a documented, tested reason it
  cannot;
- all transition work is keyed to a generation/preparation ID;
- the complete automated transition matrix passes;
- `npm run check` and `npm run build` pass;
- the deployed protocol version and Firebase rules agree;
- same-machine and real-device verification show clean first-track and
  stream/source-file switching behavior;
- the final architecture no longer depends on scattered readiness resets or a
  sequence of empirically tuned teardown timers.

Until then, `0.3.1a` remains the field notebook: valuable evidence, not the
implementation to preserve.
